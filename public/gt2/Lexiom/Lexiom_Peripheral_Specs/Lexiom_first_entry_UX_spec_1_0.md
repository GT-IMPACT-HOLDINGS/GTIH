# Lexiom First-Entry Player Profile UX Spec

- **Version:** 1.1
- **Status:** MVP (as implemented)

## 1. Purpose

Define the current first-entry onboarding that captures a stable player profile before case creation.

The implemented flow is intentionally compact:

- role selection
- unique strategic value proposition
- generated draft identity statement (not user-edited in current landing UI)
- outbound draft voice approval

---

## 2. Scope

This spec includes:

- first-entry detection and branching (new vs returning)
- role selection
- open-ended strategic value proposition input
- GT3 generation of `draftIdentity` (persisted in profile model; no dedicated editable step in current landing UI)
- outbound draft voice (editable) and profile approval
- profile persistence in local storage
- personalized welcome
- single mode-entry CTA (`Enter the Lexiom`, routes to Zenith mode)
- redirect to case creation screen after mode select

This spec does **not** include:

- profile editing after first approval
- account/user management
- payment/subscription onboarding
- detailed case-creation UX (covered by `Lexiom_Case_Creation_UX_spec_1_0.md`)

---

## 3. UX Principles (Implemented)

### 3.1 Seen before mode entry

Lexiom captures role + value proposition, then uses those to shape profile semantics before entry.

### 3.2 Minimal ceremony

Onboarding uses a compressed `0/3 -> 3/3` footer progression:

- Step 0 = `0/3`
- Step 1 = `1/3`
- Step 2 + Step 3 = `2/3`
- Step 4 + Step 5 = `3/3`

### 3.3 Draft identity remains in data model

`draftIdentity` is generated by GT3 and persisted on approval. In current landing implementation it is not shown as a standalone editable step.

### 3.4 Approval gate

Mode entry is blocked until profile approval is completed.

---

## 4. Implemented Flow Overview

1. **Step 0**: New vs Returning.
2. **Step 1 (1/3)**: select one role card.
3. **Step 2 (2/3)**: enter unique strategic value proposition.
4. System calls GT3 to generate `draftIdentity` after value-proposition entry.
5. System calls GT3 to generate outbound polar draft voice for step 4 (when no saved outbound voice exists).
6. **Step 4 (3/3)**: user reviews/edits outbound draft voice and approves profile.
7. Lexiom persists approved profile (including generated `draftIdentity`).
8. **Step 5**: Lexiom shows personalized welcome text.
9. User clicks **Enter the Lexiom** (single CTA).
10. Redirect path goes through `case-create.html` (with transition animation + `skipIntro=1` handoff).

---

## 5. Step-by-Step Behavior

### 5.1 Step 1: Role Selection

Roles:

- Lawyer
- Mediator
- Sales Professional
- Non-Professional

Requirement: exactly one role must be selected to continue.

### 5.2 Step 2: Unique Strategic Value Proposition

User provides free-text value proposition.

Requirement: non-empty input is required.

On continue:

- GT3 must generate `draftIdentity` (stored in landing state; later promoted to profile on approval).
- GT3 should generate outbound polar draft text for step 4 when no saved draft voice exists.

### 5.3 Draft identity generation (no standalone editable step)

Current behavior:

- `draftIdentity` is generated by GT3 from role + value proposition.
- generated `draftIdentity` is retained in landing state and promoted into approved profile on step-4 approval.
- there is no standalone editable identity step in current `landing.html` (`landing-step-3` is absent).

### 5.4 Step 4 (3/3): Outbound Draft Voice + Approval

User can edit outbound draft voice textarea.

On approve:

- profile is persisted with:
  - `approved: true`
  - `role`
  - `valueProposition`
  - `draftIdentity`
  - `principalLabel` (normalized outbound voice)
- welcome message is generated/displayed.

---

## 6. Persistence Model (Implemented)

Primary keys used by onboarding:

- `lexiom_first_entry_state_v1` (working onboarding state)
- `lexiom_first_entry_profile_v1` (approved profile gate)
- `lexiom_landing_event_queue_v1` (event queue telemetry)

`draftIdentity` remains part of persisted profile and is consumed by downstream advisory shaping.

---

## 7. Mode Entry (Implemented MVP)

Current implementation offers a single first-entry CTA:

- **Enter the Lexiom**

Accord option is not exposed on the first-entry mode screen in current UI.

After mode selection, redirect proceeds to case creation:

`landing.html -> case-create.html -> index.html`

---

## 8. Functional Requirements (Aligned to Implementation)

- **FR-1:** Detect first-time state via approved profile key.
- **FR-2:** Present New / Returning branch.
- **FR-3:** Require exactly one role selection.
- **FR-4:** Require non-empty strategic value proposition input.
- **FR-5:** Generate `draftIdentity` from role + value proposition before approval.
- **FR-6:** Generate and persist `draftIdentity` before outbound voice approval (without a standalone editable identity step in current landing UI).
- **FR-7:** Present outbound draft voice editing/approval as visible step `3/3`.
- **FR-8:** Persist approved profile before mode entry.
- **FR-9:** Block mode entry until approval completes.
- **FR-10:** Show personalized welcome after approval.
- **FR-11:** Provide a single entry CTA labeled **Enter the Lexiom** (Zenith-mode route) and continue into case-create handoff flow.
- **FR-12:** Keep profile-shaped personalization inputs (`role`, `valueProposition`, `draftIdentity`, `principalLabel`) available for downstream GT3 behavior.

---

## 9. Out of Scope

- post-onboarding profile editor
- account/tenant/billing lifecycle
- case creation semantics/details (separate spec)
- multi-profile support
- dynamic per-case role-card taxonomies

---

## 10. Summary

Current first-entry onboarding uses a compressed footer progression (`0/3`, `1/3`, `2/3`, `3/3`) with generated identity persistence, outbound draft review, and approval gating.

Identity inference/persistence remain part of the profile model, but the dedicated editable identity reflection page is not present in the current landing UI.

---

## 11. Known divergence and temporary behavior

- **Temporary behavior (dev/test):** `bypassFirstEntry=1` is honored by entry guards in `case-create.html` and `app.js`.
- **Known divergence:** first-entry eligibility is checked in multiple places (`lexiom_first_entry_profile_v1` and additional pre-SPA checks in `app.js`), which is behaviorally consistent but architecturally duplicated.
- **Assumption:** inbound artifact session handoff (`inboundArtifact` -> `lexiom_pending_inbound_artifact_v1`) is treated as transport continuity for shared links, not as first-entry UX logic.
